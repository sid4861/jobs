Part A Theory

Building blocks: data types, data structures, ADTs §1.1–1.4

A variable is a named placeholder for a value. A data type fixes which values a variable can hold and which operations make sense on them. A 32-bit signed integer, for example, covers −2³¹ … 2³¹−1. Languages give you primitive (system-defined) types like int, float and char, and let you build user-defined types from them, such as structs and classes.

A data structure is a way of organising data so that the operations you care about are efficient. The book splits them into two families:

Linear

Elements form a sequence and are reached one after another: arrays, linked lists, stacks, queues.

Non-linear

Elements branch or interconnect: trees and graphs.

An Abstract Data Type (ADT) separates what from how. It has two parts, a declaration of data and a declaration of operations, and makes no promise about the implementation. A stack ADT says "push, pop, peek". Whether an array or a linked list sits underneath is a separate decision with different costs.

You already know this

An ADT is a TypeScript interface, and a data structure is the class that implements it. "Design a structure with O(1) insert, delete and getRandom" is really an ADT question. You choose and combine implementations, here a hash map plus an array, to meet the interface's cost targets.

Algorithms and why we analyse them §1.5–1.9

An algorithm is a finite, unambiguous, step-by-step procedure that solves a problem. We judge it on two things: correctness (it gives the right output for every valid input) and efficiency (how much time and memory it uses).

How should two algorithms be compared? The book rules out the obvious options one at a time:

MeasureProblem
Wall-clock execution timeDepends on the machine, the load and the language runtime
Number of statements executedDepends on the programming language and the programmer's style
Running time as a function f(n) of input size nIndependent of machine and style. This is the one we use.

Input size depends on the problem: array length, number of nodes and edges (V and E), number of bits in a number, matrix dimensions. Always say which n you mean. "O(V + E)" is more precise than "O(n)" for graphs.

Rate of growth §1.10–1.11

The rate of growth is how fast running time rises as input grows. For large n the highest-order term swamps everything else, so we drop lower-order terms and constants: n⁴ + 2n² + 100n + 500 ≈ n⁴. It's like the bill for a house and a coffee: the total is "about the house".

Types of analysis §1.12

The same algorithm can behave very differently on different inputs of the same size. Take linear search for x:

Best case

x is the first element: 1 comparison. Rarely useful on its own.

Average case

Over random inputs, about n/2 comparisons, which is Θ(n). Needs an input distribution.

Worst case

x is last or missing: n comparisons. This is the default in interviews.

Know which case a famous bound refers to. Hash tables are O(1) average but O(n) worst. Quicksort is O(n log n) average but O(n²) worst. Interviewers listen for that distinction.

Asymptotic notation: O, Ω, Θ §1.13–1.18

Big-O
Upper bound. f(n) = O(g(n)) if there exist constants c > 0 and n₀ such that 0 ≤ f(n) ≤ c·g(n) for all n ≥ n₀.
Omega Ω
Lower bound. f(n) = Ω(g(n)) if f(n) ≥ c·g(n) ≥ 0 for all n ≥ n₀.
Theta Θ
Tight bound. c₁·g(n) ≤ f(n) ≤ c₂·g(n) for all n ≥ n₀, so f is both O(g) and Ω(g).
Worked example

Show 3n² + 2n + 5 = O(n²). Pick c = 4. We need 4n² ≥ 3n² + 2n + 5, i.e. n² − 2n − 5 ≥ 0, which holds for n ≥ 4. So c = 4, n₀ = 4 works. In interviews "Big-O" is normally used to mean the tight worst-case bound. Don't answer "O(n³)" for a quadratic algorithm, even though it's technically true.

Reading complexity straight off code §1.19

The book's guidelines turn analysis into mechanical rules:

  1. Loops: cost of the body × number of iterations.
  2. Nested loops: multiply the iteration counts, working from the inside out.
  3. Consecutive statements: add them. The largest term wins.
  4. If-then-else: the test plus the more expensive branch (worst case).
  5. Logarithmic: if the problem size is multiplied or divided by a constant each step, the loop runs O(log n) times.

Guess and confirm §1.26


When no theorem fits, guess a bound (by expanding a few levels or drawing the recursion tree), then prove it by induction. For example, guess that T(n) = 2T(n/2) + n is ≤ c·n log n. Substituting gives 2·c(n/2)log(n/2) + n = c·n log n − c·n + n ≤ c·n log n whenever c ≥ 1. ✓



Amortised analysis §1.27


Amortised cost is the average cost per operation over a worst-case sequence of operations. No probability is involved. One operation may be expensive, but expensive operations are rare enough that the total stays low.


The classic case is a dynamic array that doubles its capacity when full. The copies cost 1 + 2 + 4 + … + n < 2n over n pushes, so each push is O(1) amortised. If the array grew by just +1 each time, the copies would cost 1 + 2 + … + n = O(n²) in total (the book makes this point in Ch 4, Problem 19).

Part A Theory



What recursion is, and why we use it §2.1–2.3


A function is recursive when it solves a problem by calling itself on a smaller instance of the same problem. Each call must make progress toward a case simple enough to answer directly. Recursion fits problems that are naturally self-similar: trees, nested structures, divide-and-conquer, and "try every choice" search.


You already know this
Walking a nested JSON object, rendering a React tree of components, or fs.readdir-ing a folder tree are all recursion. The question you answer each time is: "if I trust the call on the sub-part, what do I do at this level?"



The format of a recursive function §2.4




Base case(s)
Inputs small enough to answer directly with no further calls. Every path must reach one, or you hit infinite recursion and a stack overflow.


Recursive case
Break the input into smaller pieces, call yourself on them, and combine the results. Each call must move toward a base case.







Recursion and memory: the call stack §2.5


Each call gets its own stack frame holding its parameters, local variables and return address. Frames are pushed when a call starts and popped when it returns, so the deepest active chain of calls determines your space usage. Classic recursive algorithms §2.8


Factorial, Fibonacci, merge sort, quick sort, binary search, tree traversals, DFS, and the Towers of Hanoi. Hanoi is the cleanest example of trusting the recursion: to move n disks from A to C, move n−1 disks to B (recursively), move the biggest disk to C, then move n−1 disks from B to C. That gives T(n) = 2T(n−1) + 1, so 2ⁿ − 1 moves.





Backtracking §2.10–2.11


Backtracking is a smarter brute force. You build a solution one choice at a time, and as soon as a partial solution can't possibly lead to a valid answer you abandon it (prune) and undo the last choice. The search follows a tree of decisions with a three-beat rhythm: choose → explore → un-choose.



The book lists typical backtracking problems: binary strings, k-ary strings, the knapsack problem, generalised strings, graph colouring, Hamiltonian cycles, and N-Queens. Watch N-Queens below. Each queen is placed in the next row, and the solver backs up as soon as there's a conflict.

What sorting is and why it matters §10.1–10.2


Sorting arranges elements in a defined order (numeric, lexicographic, or by a custom key). Its real value is that sorted data makes other problems easy. Searching becomes binary search, duplicates sit next to each other, intervals can be swept left to right, and two pointers start to work. Many "clever" interview solutions are just sort first, then one linear pass.

The elementary sorts §10.5–10.8




Bubble sort
Repeatedly swap adjacent out-of-order pairs. After pass k, the k largest items have "bubbled" to the end. Add a "no swaps happened" flag to stop early, which makes the best case O(n). Stable, in-place, O(n²).


Selection sort
Find the minimum of the unsorted part and swap it into place. Always O(n²) comparisons but only n−1 swaps, the fewest of the simple sorts. Not stable.


Insertion sort
Grow a sorted prefix by sliding each new element left into position. Stable, in-place, adaptive (O(n + inversions)), and online. Excellent for small or nearly-sorted arrays, which is why TimSort uses it internally.


Shell sort
Insertion sort over elements a gap apart, with the gap shrinking to 1. Distant elements move early. Complexity depends on the gap sequence (about O(n^1.3) in practice).





The O(n log n) sorts §10.9–10.12




Merge sort
Split in half, sort each half recursively, then merge the two sorted halves in linear time. Always Θ(n log n). Stable, needs O(n) extra space. Best for linked lists and external sorting.


Quick sort
Pick a pivot and partition so smaller items go left and larger go right, then recurse on each side. Θ(n log n) on average and in-place, but O(n²) when pivots are bad (e.g. sorted input with a first/last pivot). Choosing the pivot at random fixes this in expectation.


Heap sort
Build a max-heap in O(n), then repeatedly swap the root to the end and sift down. Θ(n log n) worst case, in-place, not stable (Module 11).




Tree sort inserts everything into a BST and reads it back with an inorder traversal. That's O(n log n) on average but O(n²) if the tree degenerates.

Why comparison sorts can't beat n log n
Any comparison sort corresponds to a binary decision tree whose leaves are the n! possible orderings. A binary tree with n! leaves has height at least log₂(n!) ≈ n log₂ n, so some input needs that many comparisons. To go faster you have to stop comparing, which is exactly what the linear sorts below do.



Linear-time sorts §10.14–10.17





Counting sort
Keys are integers in [0, k). Count, take prefix sums, place. O(n + k).


Bucket sort
Spread keys that are uniformly distributed over [0,1) into n buckets, sort each small bucket, and concatenate. O(n) expected.


Radix sort
Run a stable counting sort on each digit, least significant first. O(d·(n + b)) for d digits in base b. The book uses this to sort values in [1, n²] in O(n) (Ch 10 · P6).





Topological sort and external sorting §10.18–10.19


Topological sort orders the vertices of a DAG so that every edge goes forward. It's covered with graphs in Module 14. External sorting handles data bigger than memory. Read chunks that fit in RAM, sort each into a "run", write it back to disk, then k-way merge the runs using a min-heap of each run's current head. This is the standard answer to "sort a 2 GB file on a machine with little RAM" (Ch 10 · P21).

Searching: kinds and costs §11.1–11.5


Searching means finding an item with given properties in a collection. The book lists the main types: unordered linear search, sorted linear search, binary search, interpolation search, symbol tables and hashing (Module 5), and string searching (Module 12).




Unordered linear search
Scan until you find it: O(n) worst case. This is the only option when there's no structure to exploit.


Sorted linear search
Same scan, but you can stop as soon as an element exceeds the target. Still O(n) worst case, though misses end sooner on average.





Binary search §11.6


On a sorted array, compare the target with the middle element and throw away the half that can't contain it. The search space halves every step, so it takes ⌈log₂(n+1)⌉ comparisons. A million elements need about 20.


The idea is easy and the details are error-prone, so learn binary search as an invariant: "if the target exists, it is inside [lo, hi]". Every update has to preserve that invariant, and the loop ends when the range is empty.




Binary search is about monotonic predicates, not arrays
Whenever there's a yes/no question whose answers look like F F F F T T T as you increase some value, you can binary-search for the first T. Examples: "first index where a[i] ≥ x" (lower bound), "smallest capacity that ships all packages in D days", "integer square root", "first bad version". This search on the answer pattern is one of the most powerful in interviews.





Interpolation search §11.7–11.8


Binary search always probes the middle. Interpolation search guesses where the target should be, the way you'd open a dictionary near "S" for "Smith": pos = lo + (x − a[lo]) · (hi − lo) / (a[hi] − a[lo]). On uniformly distributed keys that's O(log log n). On skewed data it can degrade to O(n).

Array techniques from the book's problem set §11.11


Chapter 11's 80 problems are a catalogue of array tricks that come up again and again. Learn them as named techniques:




Two pointers (converging)
On sorted data, start at both ends and move the pointer that brings you closer to the goal. Used for pair sum (P25–28), closest-to-zero pair (P30–31) and 3-sum (P32–36).


Partitioning pointers
Low/mid/high regions swapped in one pass: even–odd segregation (P67–69) and the Dutch national flag 0-1-2 sort (P70).


Sign-flip marking
If values are in 1..n, use the array itself as a visited set by negating A[|x|−1]. Finds duplicates in O(1) extra space (P3, P8).


XOR / sum identities
Missing number = expected sum − actual (or XOR of everything). The element occurring an odd number of times = XOR of all elements (P13–18).


Boyer–Moore voting
Majority element (> n/2) in O(n) time and O(1) space: keep a candidate and a counter, and decrement on mismatch (P54–58).


Staircase search
In a matrix sorted by rows and columns, start at the top-right corner. Each comparison eliminates a whole row or column, so it's O(n + m) (P63).






Sliding window, the "same-direction" two pointers
For "longest/shortest contiguous subarray or substring satisfying X", grow the right edge, and while the window breaks X, shrink the left edge. Each index enters and leaves the window once, so it's O(n). The book's minimum-window problem (Ch 15 · P13) and window-maximum (Ch 5 · P4) are both built on this.

A selection algorithm finds the k-th smallest element (the median is k = n/2) without fully sorting. The book builds up through progressively better solutions:

Quickselect recurses into only the side that contains index k, so the expected work is n + n/2 + n/4 + … = O(n). Median of medians picks a pivot that's always good: split into groups of 5, take each group's median, and recursively find the median of those. Why hashing? §14.1–14.4


If keys were small integers you could use them directly as array indices (a direct-address table): perfect O(1), but you'd need an array as big as the key universe. For keys like strings or 64-bit IDs that's impossible. Hashing squeezes the huge universe into a small table: a hash function maps each key to an index in [0, m).




Components: table, hash function, load factor §14.5–14.8




Hash table
An array of m slots (buckets).


Hash function
Turns a key into an integer, reduced mod m. A good one is deterministic, fast, and spreads keys uniformly. For strings, a polynomial rolling hash such as h = h·31 + charCode is standard. A prime table size helps break up patterns in keys.


Load factor α
α = n / m, the number of items per slot. The expected cost of an operation grows with α. When α passes a threshold (often 0.75), rehash into a table about twice as large. That's O(n) once, so O(1) amortised, the same doubling argument as dynamic arrays.





Collisions and how to resolve them §14.9–14.13




Separate chaining
Each bucket holds a list of entries. Insert by prepending to the list. Search scans one chain of expected length α. Works fine even with α > 1, and deletion is easy.


Open addressing
Everything lives in the array itself. On a collision, probe other slots in a fixed sequence. Requires α < 1, and deletion needs tombstones so that later searches don't stop early.

How hashing gets O(1), and when it doesn't §14.14–14.16


With a uniform hash function and a bounded load factor, the expected chain length or probe count is a constant, so the average cost is O(1). The worst case is still O(n): if every key collides (bad hash function, or an adversary picking keys) you're scanning one long list. That's why some runtimes randomise their hash seeds.


When not to use a hash table. When you need order: min/max, sorted iteration, range queries ("all keys between 10 and 20"), or predecessor/successor. Use a balanced BST or a sorted array for those.



Bloom filters §14.17


A Bloom filter is a compact, probabilistic set. It's a bit array of m bits plus k hash functions. To add an item, set its k bits. To query, check those k bits: if any bit is 0 the item is definitely absent, and if all are 1 it's probably present. You get no false negatives, some false positives, no deletion (in the basic version), and a tiny amount of memory. The false-positive rate is roughly (1 − e^(−kn/m))^k.




System-design tie-in
Cassandra and other LSM-tree stores (built on the LevelDB/RocksDB design) use Bloom filters to skip disk reads for keys that don't exist. CDNs use them to avoid caching one-hit wonders, and crawlers use them to remember visited URLs. Mentioning them in a design round is a strong signal.

What a linked list is §3.1–3.2


A linked list is a chain of nodes. Each node stores data and a pointer (next) to the following node, and the last node points to null. You hold a reference to the head and reach everything else by following pointers. The ADT's main operations are insert, delete, count and find-the-k-th. Auxiliary ones include delete-list and find-from-end.


You already know this
React's Fiber tree links work units with child/sibling/return pointers. Middleware chains (Express next()) and blockchain blocks pointing to their predecessor also have linked-list shape.



Why linked lists? Arrays vs lists §3.3–3.5


An array is one contiguous block, so element i lives at base + i × size. That's O(1) access and very cache-friendly. The cost is that the size is fixed, and inserting in the middle means shifting everything after it. A dynamic array (JS arrays, Java ArrayList) doubles when full to fix the size problem. A linked list scatters nodes across memory and links them, so it grows one node at a time and splices in O(1) once you're at the right spot.

Singly linked lists §3.6


Traversal is O(n): for (let p = head; p; p = p.next). Insertion and deletion come down to rewiring pointers in the right order. To insert x after node p, first point x.next = p.next, then set p.next = x. Do it in the other order and you lose the rest of the list. Deleting at the head means moving head. Doubly and circular lists §3.7–3.8



A doubly linked list adds a prev pointer, so you can delete a node you hold in O(1). It's the backbone of an LRU cache. In a circular list the last node points back to the head. Loops must stop on "back at start" rather than on null.



Memory-efficient, unrolled, and skip lists §3.9–3.11




XOR (memory-efficient) DLL
Store a single field ptrdiff = prev ⊕ next. Moving forward: next = ptrdiff ⊕ prev. Doubly-linked behaviour with one pointer per node. A curiosity, and impossible in garbage-collected languages.


Unrolled linked list
Each node holds a small array (a block) of elements. With blocks of about √n, search and insert are O(√n), and cache behaviour is much better.


Skip list
Several levels of "express lanes" over a sorted list. Each node is promoted to the next level with probability ½. Search, insert and delete are O(log n) in expectation, with no rebalancing.

What a stack is §4.1–4.3


A stack is an ordered list where insertion and deletion happen at one end only, the top. The last item in is the first out: LIFO. The ADT's main operations are push(x) and pop(). Auxiliary ones are top()/peek(), size() and isEmpty(). Popping an empty stack is an underflow, and pushing onto a full fixed-size stack is an overflow.



You already know this
The JS call stack in every error trace, browser history (Back pops the stack), editor undo, and React's context nesting are all stacks. Any time you match an "opener" with its "closer" (HTML tags, brackets, try/finally), a stack is doing the work.

What a queue is §5.1–5.4


A queue is an ordered list where insertion happens at the rear and deletion at the front. The first in is the first out: FIFO. The ADT's main operations are enqueue(x) and dequeue(). Auxiliary ones are front(), size() and isEmpty(). As with stacks, dequeuing an empty queue is an underflow and enqueuing into a full array is an overflow.



You already know this
The JavaScript event loop (task and microtask queues), BullMQ/SQS/Kafka consumers, a print spooler, a rate-limiter's sliding log, and Node stream buffers are all queues. A ring buffer is the standard implementation in high-throughput systems.

  • Asynchronous data transfer (pipes, file I/O, sockets)

Indirect

Implementations §5.6


A naive array queue wastes space: as front moves forward, the slots it leaves behind are never reused. The fix is a circular array, where indices wrap with (i + 1) % capacity. One subtlety: when front === rear, is the queue empty or full? Either keep a size counter, or leave one slot permanently empty (book P6). A dynamic circular array doubles when full. A linked-list queue enqueues at the tail and dequeues at the head, both O(1).




JavaScript trap

What a tree is, and its vocabulary §6.1–6.2


A tree is a hierarchical structure: nodes connected by edges, with one root and no cycles, so every node except the root has exactly one parent. Lists are linear; trees branch.

The node with no parent.


Edge
A parent→child link. A tree with n nodes has n − 1 edges.


Leaf

Ancestor

Height

Traversals §6.6


A traversal visits every node exactly once, so it's O(n) time and O(h) space for the recursion or the explicit stack. The three depth-first orders differ only in when you process the current node (D) relative to its left (L) and right (R) subtrees:




Preorder (D L R)
Node first. Used to copy or serialise a tree and for prefix expressions. Iteratively: a stack, pushing right before left.


Inorder (L D R)
Left subtree, node, right subtree. On a BST this gives sorted order. Iteratively: push the left spine, pop, then move to the right child.


Postorder (L R D)
Children first. Used for deleting a tree, computing heights and sizes, and evaluating expressions: anything that needs children's results before the parent.


Level order (BFS)
Level by level with a queue. Used for anything per-level: zigzag, right-side view, maximum level sum, minimum depth.







Generic (N-ary) trees §6.7


When a node can have any number of children, an array of child pointers wastes space. The book's representation is first-child / next-sibling: each node keeps just two pointers, to its first child and to its next sibling. That turns any N-ary tree into a binary tree.




Threaded, expression, and XOR trees §6.8–6.10




Threaded binary trees
Half the pointers in a tree (n + 1 of them) are null. A threaded tree reuses them as "threads" to the inorder predecessor and successor, which allows stack-free, queue-free traversal. The same idea underlies Morris traversal's O(1)-space inorder.


Expression trees
Leaves are operands and internal nodes are operators. Inorder gives infix, postorder gives postfix, and evaluation is a postorder walk. To build one from postfix, push operands and, for each operator, pop two and make them its children. Babel, ESLint and TypeScript all work on ASTs like this.


XOR trees
Like the XOR linked list: each node stores XORs of neighbouring pointers, so it can move both up and down with fewer fields. Know that it exists; it's not interview material.

Balanced BSTs and AVL trees §6.12–6.13

Red-black trees
A looser balance: nodes are coloured red or black, no red node has a red child, and every path has the same number of black nodes, so h ≤ 2·log(n+1). Fewer rotations than AVL. Used by Java TreeMap, C++ std::map and the Linux CFS scheduler.

Interval trees

Scapegoat trees
No per-node balance data. When a subtree gets too deep, rebuild it into a perfectly balanced one.

The string-matching problem §15.1–15.3


Given a text T of length n and a pattern P of length m, find every position where P occurs in T. This is indexOf, grep, Ctrl-F, and DNA search. The brute-force method tries every alignment and compares character by character, which is O((n − m + 1)·m) = O(nm) in the worst case (e.g. T = "aaaa…ab", P = "aaab"). Every better algorithm avoids re-examining characters it has already matched.



Rabin–Karp: compare hashes, not strings §15.4


Hash the pattern once. Then slide a window of length m across the text, keeping a rolling hash that's updated in O(1) per step: remove the outgoing character's contribution, shift, and add the incoming one. Do a real character comparison only when the hashes match. That's O(n + m) on average and O(nm) worst case if there are many spurious hits. It's especially good for multi-pattern search and plagiarism detection.







Finite automata and KMP §15.5–15.6


A string-matching automaton precomputes, for every state (how many pattern characters have matched so far) and every input character, which state to move to next. Matching then reads each text character exactly once, O(n), but building the table costs O(m·|Σ|).


Knuth–Morris–Pratt gets the same "never move backwards in the text" guarantee with only an O(m) table. The prefix function (failure function, LPS) stores, for each prefix of P, the length of the longest proper prefix that is also a suffix. On a mismatch after matching j characters, you already know the text's last lps[j−1] characters equal the pattern's first lps[j−1]. So you slide the pattern forward to that point and keep going without re-reading the text. The total is O(n + m).





Boyer–Moore §15.7


Compare the pattern right to left. On a mismatch, use the bad-character rule (shift so the mismatched text character lines up with its last occurrence in P, or skip past it completely) and the good-suffix rule (shift to the next occurrence of the matched suffix). On real text it often skips most characters, which makes it sub-linear in practice. It's the classic algorithm behind fast grep-style search.

Data structures for storing strings §15.8–15.13


Suppose you need to store a dictionary of words and answer lookups, or "all words starting with pre". The options are:




Hash table
O(L) to hash a word of length L, then O(1). Fast exact lookup, but no prefix queries and no ordering.


BST of strings
O(L·log n): log n comparisons, each up to L characters. Supports ordering and ranges.


Trie (prefix tree)
Each edge is a character, so each path from the root spells a prefix. Insert and search are O(L), independent of n. Prefix queries are natural. The cost is memory: up to |Σ| child pointers per node.


Ternary search tree
Each node holds one character plus lo/eq/hi pointers: a BST at every trie level. Much less memory than a trie, and still supports prefix and near-neighbour search.






You already know this
Search-box autocomplete, router libraries that match URL path segments (find-my-way, used by Fastify, is a radix tree), IP routing tables (longest-prefix match), and spell-checkers all use tries or their compressed form, radix/Patricia trees.



Suffix trees §15.14


A suffix tree is a compressed trie of all suffixes of a text. It can be built in O(n) (Ukkonen's algorithm), and then answers many questions quickly. Is P a substring? O(m). Longest repeated substring? The deepest internal node. Longest common substring of two strings? Build the tree over S₁#S₂$. Longest palindrome? Use S and its reverse. In interviews you mostly need to know that it solves these. Implementing one is rarely asked.

Equivalence relations and classes §8.1–8.2


A relation R is an equivalence relation if it is reflexive (a R a), symmetric (a R b ⇒ b R a) and transitive (a R b, b R c ⇒ a R c). "Is connected to" in an undirected graph is one, and so is "lives in the same state as" (the book's P1). An equivalence relation splits a set into non-overlapping equivalence classes. The disjoint-set structure maintains exactly those classes as they merge.



The Disjoint Sets ADT §8.3–8.4




MAKESET(x)
Create a singleton set {x}.


FIND(x)
Return the representative (root) of x's set. Two elements are in the same set exactly when their FINDs are equal.


UNION(x, y)
Merge the sets containing x and y.




Applications: connected components of a graph that only gains edges, Kruskal's MST, network connectivity, cycle detection in undirected graphs, image segmentation, percolation, merging accounts that share an email, and "friend circles".

Union by size / height (rank)

Graph glossary §9.1–9.2


A graph G = (V, E) is a set of vertices and a set of edges connecting pairs of them. Trees are a special case: connected, acyclic, with exactly V − 1 edges.





Path / cycle
A sequence of vertices joined by edges. A simple path repeats no vertex. A cycle starts and ends at the same vertex.


Degree
Number of incident edges. Digraphs have in-degree and out-degree. Σ degree = 2E.


Connected
A path exists between every pair. Components are the maximal connected pieces. In digraphs, strongly connected means mutually reachable.


Sparse / dense
E ≈ V versus E ≈ V². This decides the representation.


Complete graph
Every pair is connected: V(V−1)/2 edges (book P1).


Bipartite
The vertices split into two sides with edges only between sides. Equivalent to being 2-colourable, or having no odd cycle.


Spanning tree
A subgraph that is a tree containing every vertex.

Traversals: DFS and BFS §9.5




Depth-first search
Go as deep as possible, then backtrack, using recursion or an explicit stack. Classifying edges as tree, back, forward or cross gives you cycle detection (a back edge), topological order (reverse finish time), strongly connected components, articulation points and bridges (low-link values), and Euler paths.

Topological sort §9.6


A topological order of a DAG lists the vertices so that every edge u→v has u before v. It exists if and only if there's no cycle. Kahn's algorithm repeatedly removes a vertex with in-degree 0 and decrements its neighbours' in-degrees. If vertices remain at the end, there's a cycle. The alternative is DFS: output vertices in reverse order of finishing. Both are O(V + E). The animation uses a full-stack "learning path" DAG.

Minimum spanning trees §9.8


A minimum spanning tree connects all vertices of a weighted, connected, undirected graph with the smallest possible total edge weight, using V − 1 edges and no cycle. Think of laying the least cable that still connects every office. Both classic algorithms are greedy and both rely on the cut property: the lightest edge crossing any cut is safe to add.




Prim
Grow a single tree from any start vertex, always adding the cheapest edge that leaves the tree, using a min-heap keyed by edge weight. O(E log V). The code is almost identical to Dijkstra; book P39 asks for the difference: Prim's key is the edge weight, Dijkstra's is the path length.


Kruskal
Sort all edges by weight, then add each edge unless it would form a cycle. Union-Find answers that in near-O(1). O(E log E).







Advanced DFS applications §9.9




Articulation points & bridges
A vertex or edge whose removal disconnects the graph: single points of failure in a network. Track disc[u] and low[u], the earliest discovery time reachable through u's subtree plus one back edge. Edge u–v is a bridge if low[v] > disc[u].


Strongly connected components
Kosaraju: run DFS for finish order, reverse the graph, then DFS in decreasing finish order. Each tree is one SCC. Tarjan does it in a single pass with low-links.


Euler circuits
A circuit using every edge exactly once exists if and only if the graph is connected and every vertex has even degree (the Königsberg bridges). Build it with Hierholzer's algorithm, a DFS that splices in sub-circuits.


Hamiltonian cycles / TSP
Visit every vertex exactly once. This sounds similar but is NP-complete (Module 19). Expect backtracking, or bitmask DP for small V.

A map of algorithm design techniques §16.1–16.5


Chapter 16 classifies algorithms in several ways before the last three chapters look at the main design methods in depth.




The greedy strategy §17.1–17.3


A greedy algorithm builds a solution step by step and always makes the choice that looks best right now. It never reconsiders. When it works it's simple and fast, usually a sort followed by one pass. It works when the problem has two properties:




Greedy-choice property
Some globally optimal solution starts with the locally best choice. You show this with an exchange argument: take any optimal solution and swap its first choice for the greedy one without making it worse.


Optimal substructure
After the greedy choice, what remains is a smaller instance of the same problem, and solving it optimally completes an optimal solution.





Does greedy always work? §17.4–17.5


No, and this is the trap interviewers set. Greedy change-making works for "canonical" coin systems like India's (1, 2, 5, 10, …), which is book P11. It fails for coins {1, 3, 4} and amount 6: greedy takes 4 + 1 + 1, three coins, while 3 + 3 uses two. Try your own coin systems below. Greedy also fails on 0/1 knapsack but is optimal for fractional knapsack.

Classic greedy applications §17.6–17.7


Sorting (selection sort picks the minimum greedily), priority queues, Huffman coding, Dijkstra, Prim, Kruskal, interval scheduling, fractional knapsack, and job scheduling with deadlines.


Interval scheduling: which greedy?


Given intervals, pick as many non-overlapping ones as possible. Three plausible rules are "earliest start", "shortest first" and "earliest finish". The book's P4–P7 shows that only earliest finish is always optimal: finishing first leaves the most room for everything else. Switch between strategies on the same intervals and compare the counts.




Huffman coding


To compress text, give frequent characters short bit codes and rare ones long codes, with no code being a prefix of another so decoding is unambiguous. Huffman's greedy algorithm repeatedly merges the two least frequent trees into one, using a min-heap. The resulting tree gives an optimal prefix code: left = 0, right = 1. Total cost is O(n log n).

What dynamic programming is §19.1–19.2


Dynamic programming is recursion with a memory. If a recursive solution keeps solving the same subproblems, solve each one once, store the answer in a table, and look it up afterwards. That alone often turns exponential time into polynomial time. The book's summary: DP is the difference between plain recursion and memoized recursion.


You already know this
You've memoized expensive selectors (reselect, useMemo) and cached API responses by request key. Top-down DP is exactly that: a cache keyed by the function's arguments. The skill to learn is choosing what the arguments (the state) should be.



The two properties §19.3–19.4




Optimal substructure
An optimal solution is built from optimal solutions to its subproblems. The shortest path A→C through B contains the shortest path A→B.


Overlapping subproblems
The recursion revisits a small set of distinct subproblems many times. Without overlap (merge sort, factorial) memoization doesn't help, and plain D&C or recursion is enough.




DP can't solve every problem. When the state space is itself exponential (TSP over all subsets), DP still helps (O(n²·2ⁿ) instead of O(n!)) but the problem stays hard.

Easy vs hard problems §20.1–20.2


An algorithm is efficient (tractable) if it runs in polynomial time, O(nᵏ) for some constant k. Exponential-time algorithms (2ⁿ, n!) are intractable: adding a few input items doubles the work. Complexity theory asks which problems, not which algorithms, have polynomial-time solutions at all.



Decision problems and procedures §20.3–20.5


The theory is phrased in terms of decision problems, problems with a yes/no answer. "Is there a path of length ≤ k?" rather than "find the shortest path". Optimisation problems usually reduce to their decision versions (binary-search over k). A decision procedure is an algorithm that answers a decision problem. A complexity class is a set of problems that share the same resource bounds.



P, NP, Co-NP, NP-hard, NP-complete §20.6


Click a region of the diagram to see its definition and examples. The diagram assumes P ≠ NP, which is still unproven.






P
Solvable in polynomial time by a deterministic algorithm: sorting, shortest paths, MST, 2-SAT.


NP
A proposed "yes" certificate can be verified in polynomial time. Equivalently, solvable in polynomial time by a non-deterministic machine that guesses correctly. P ⊆ NP.


Co-NP
"No" answers have polynomial-time verifiable certificates. Example: "this formula is unsatisfiable".


NP-hard
At least as hard as every problem in NP: every NP problem reduces to it. It doesn't have to be in NP, or even be a decision problem (the halting problem is NP-hard).


NP-complete
In NP and NP-hard, the hardest problems in NP. A polynomial algorithm for any one of them would give one for all of NP, i.e. P = NP.





Reductions §20.7


A reduction from A to B transforms any instance of A into an instance of B in polynomial time, with the same answer. Then B easy ⇒ A easy, and A hard ⇒ B hard. To prove a new problem X is NP-complete, show X ∈ NP and reduce a known NP-complete problem to X. The Cook–Levin theorem made SAT the first NP-complete problem. 2-SAT is in P (it's solvable through strongly connected components of an implication graph), while 3-SAT is NP-complete. Likewise, finding a 3-clique is polynomial (O(n³) brute force), but k-clique for variable k is NP-complete. A small change in the problem can cross the line.



Part B Problem solving


Why this matters in an interview


    

  • If a problem smells like TSP, subset sum, graph colouring, or "visit every node exactly once", don't hunt for a polynomial algorithm. Say it's NP-hard and choose the right fallback.
    • 

  • Pseudo-polynomial DP: 0/1 knapsack and subset sum are O(n·W). That's polynomial in the numeric value W but exponential in its bit-length. It's fine when W is small, so ask about the constraints.
    • 

  • For small n, use backtracking with pruning or bitmask DP (TSP in O(n²·2ⁿ) for n ≤ 20).
    • 

  • For large n, use approximations and heuristics: greedy colouring, 2-approximation for vertex cover, nearest-neighbour for TSP, simulated annealing.

Interview playbook

  
Knowing DSA gets you about halfway. The other half is showing it inside 45 minutes while someone watches. This is the routine to rehearse until it's automatic.


  
The 45-minute timeline

  
  
    
  
  1. Understand (5′). Restate the problem. Ask about input sizes, value ranges, duplicates, negatives, empty input, and whether the input is sorted. Work one example by hand and write it down.
    2. 
  
  2. Brute force, then optimise (7′). State the naive approach and its complexity in one sentence, then climb the book's ladder: "can we improve this?" Name the bottleneck ("the inner loop re-scans") and the tool that removes it ("a hash map makes that lookup O(1)").
    3. 
  
  3. Plan (5′). Agree on the approach and the complexity before you code. Sketch the data structures and the loop invariant.
    4. 
  
  4. Code (18′). Use meaningful names and small helper functions. Narrate decisions, not keystrokes. If you get stuck, say what you're unsure about.
    5. 
  
  5. Test (7′). Dry-run your example through the code line by line, then the edge cases. Fix bugs calmly, because finding your own bug counts in your favour.
    6. 
  
  6. Wrap up (3′). Restate the time and space complexity, mention trade-offs or alternatives, and how you'd scale it.
    7. 
  


  
What interviewers score

  

  
Problem solving
Did you find an optimal approach, and could you justify it? Did you consider alternatives?

  
Coding
Clean, correct, idiomatic code. Sensible decomposition. No pseudo-code hand-waving.

  
Verification
Did you test without being asked? Did you catch your own bugs and handle the edge cases?

  
Communication
Were you easy to follow? Did you use the interviewer's hints and stay collaborative?

  

  
Signals expected at 8 years of experience
    
  
  • Clarifying questions that reveal production instincts ("Can the input fit in memory? Is this called once or in a hot path?").
    • 
  
  • Naming trade-offs: memory vs time, average vs worst case, simplicity vs constant factors.
    • 
  
  • Linking to real systems ("This is essentially an LRU. In production I'd reach for…").
    • 
  
  • Clean, testable code with no clever-but-fragile tricks unless they're asked for.

MomentSay something like

  
Starting"Let me restate this and try a small example before choosing an approach."

  
Brute force"The straightforward way is O(n²): compare every pair. Let's see where the repeated work is."
